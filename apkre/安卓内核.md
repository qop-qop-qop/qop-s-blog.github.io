传统hook，利用

```
attach()
```

主要逻辑是修改函数开头的字节实现跳转到自己的函数，而后修改返回值。这就是 inline hook

但是现有手段在应用启动之后进行一次’完整性检测“——它把自己 `.text` 段的每个字节读出来，算一遍 CRC，和编译时的预期值对比。从而检测程序是否被hook。

安卓内核使用的是arm64架构，为了绕过这种检测实现无痕迹hook，利用到了一个关键的架构特性：**ARM64 的指令 fetch 不检查 `AP` 位**。

在ARM64架构中的页表标志位（关键位）

| Bit  | 名称    | 作用                                      |
| ---- | ------- | ----------------------------------------- |
| 54   | `UXN`   | User Execute Never，置 1 就禁止用户态执行 |
| 7    | `AP[2]` | 置 1 就是只读                             |
| 6    | `AP[1]` | 置 1 就允许 EL0（用户态）进行数据访问     |

为了绕过完整性检测可以构建新的一个页表，一个给于可读，一个给于可执行。

从而使一个内存页存在两个物理页绕过完整性检测。

**R^X 的权限拆分仅发生在页表（PTE）层面，VMA 层面完全不受影响。**

因为我们没有去修改任何vm_area_struct` 的 `vm_flags。

所以进程通过/proc/self/maps，看到的内存映射仍然是r-xp

同样的通过`mprotect` 的查询、`mincore`、以及内核内部遍历 VMA 的逻辑，都看不到任何异常。

### 三种方案对比

|                         | Hypervisor (EL2)                 | 定制内核               | KPM 模块                   |
| ----------------------- | -------------------------------- | ---------------------- | -------------------------- |
| **干预层级**            | Stage-2 页表                     | 内核原生               | 运行时 hook + 直接操作页表 |
| **对 Guest/内核的侵入** | 几乎为零                         | 中等（改内核源码）     | 中等（hook 内核函数）      |
| **实现难度**            | 最低（需要 Hypervisor 开发能力） | 中等                   | 最高（依赖 KP 框架）       |
| **设备通用性**          | 差（需要虚拟机环境）             | 中等（每设备编译内核） | 较好（需 root + kallsyms） |
| **适用场景**            | Arm服务器/Mac m系列              | 自有设备/可控环境      | 通用 Android 设备          |

然后技术已在 **wxshadow** 中以第三种方案（KPM 模块）完整实现，wxshadow 在 shadow page 上支持两类修改：**断点**（写入 `BRK #7`，触发时可自动修改寄存器）和**任意补丁**（写入任意字节序列——inline hook 跳板、NOP、指令替换等）。两者可以共存于同一页面。
