# caoin-shadow 原理：从虚拟内存到读写分离 hook

> 这份文档**只讲 caoin-shadow**。caoin-hw（硬件断点）不在本文范围。
>
> 目标读者：会 C、知道指针和 Linux 基本系统调用，但没有做过 arm64 页表/内核 hook 的人。
> 全文尽量从最基础的概念讲起，再一步步推到 caoin-shadow 的实现。
>
> 证据标记：
>
> - **[架构]** ARMv8 / Linux 的通用事实，可在 ARM ARM 或内核源码中核对；
> - **[实测]** 本项目在真机（MI 8 Pro / equuleus 4.9.337 / Android 13）上验证过的结论；
> - **[实现]** 本仓库的具体做法，换实现可以不同。
>
> 一句话概括：
>
> **caoin-shadow 不修改目标代码的任何一个字节。它准备一份"原页副本 + 桩"的影子页，让同一个虚拟地址在"执行"时指向影子页、在"读取"时指回原页。CRC 自检读的是数据，hook 走的是取指，两者被页表权限分开了。**

---

## 0. 先建立整体印象

### 0.1 普通 hook 在做什么

假设目标进程里有一个函数 `foo`：

```c
int foo(int x) {
    return x + 1;
}
```

普通 inline hook 会修改 `foo` 的第一条指令，让它跳到我们自己的代码：

```
修改前：  foo:  stp x29, x30, [sp, #-16]!
修改后：  foo:  ldr x16, #8
                br  x16
                <我们的 handler 地址>
```

这样每次调用 `foo`，CPU 都会先跳到 handler。

问题在于：**代码字节被改了**。目标只要对 `foo` 所在页做一次 CRC，就会发现。

### 0.2 caoin-shadow 在做什么

caoin-shadow 不动原页，而是：

1. 分配一个新的物理页，叫**影子页**；
2. 把原页的 4KB 内容完整拷贝到影子页；
3. 在影子页的对应位置写入跳转桩；
4. 修改目标进程的页表，让 `foo` 所在的**虚拟地址**在"执行"时指向影子页；
5. 当目标要"读取"这个地址时，临时把页表指回原页。

于是：

- CPU 执行 `foo` → 执行影子页里的桩；
- 目标做 CRC 读 `foo` → 读到原页的原始字节；
- 原页从头到尾没有被写过。

这就是"读写分离"。

### 0.3 为什么这件事可行

因为 CPU 的**取指**和**数据读写**是两种不同的访问，页表可以分别控制它们的权限。arm64 的 PTE 里有专门的位：

- `UXN` 控制 EL0 能不能从这一页取指；
- `AP[2:1]` 控制 EL0/EL1 能不能读写这一页的数据。

caoin-shadow 利用这两个维度的组合，让同一个 VA 在不同时刻表现为"可执行但不可读"或"可读但不可执行"。

## 1. 虚拟内存基础

### 1.1 程序看到的地址不是物理地址

CPU 执行指令时，指令里写的地址、寄存器里的指针，都是**虚拟地址（VA，Virtual Address）**。

内存条上真实的地址叫**物理地址（PA，Physical Address）**。

两者之间由 **MMU（Memory Management Unit）** 负责翻译：

```
CPU 发出 VA
    │
    ▼
  MMU ──查页表──► PA
    │
    ▼
内存控制器访问物理内存
```

为什么要多这一层？主要有四个原因：

1. **隔离**：进程 A 和进程 B 都可以使用 `0x400000` 这个 VA，但映射到不同的物理页，互相看不见。
2. **权限**：可以规定某一页"用户态可读不可写"、"可执行不可读"。
3. **按需分配**：程序申请 1GB 内存，不代表立刻占用 1GB 物理内存；访问到哪页才分配哪页。
4. **共享**：多个进程可以把同一个物理页映射到各自的 VA，例如共享库的代码段。

**[架构]** 这也是为什么"改一个 VA 的映射"可以做到"对目标完全透明"：目标看到的 VA 没变，变的是它背后的物理页。

### 1.2 页和页帧

物理内存和虚拟内存都被切成固定大小的块：

- 虚拟内存的块叫**页（page）**；
- 物理内存的块叫**页帧（page frame）**；
- 常见大小是 4KB；
- 页帧编号叫 **PFN（Page Frame Number）**。

一个地址可以拆成两部分：

```
VA = 虚拟页号 + 页内偏移
PA = 物理页帧号 + 页内偏移
```

页内偏移在翻译前后保持不变。例如 4KB 页：

```
VA[11:0]  = 页内偏移（0x000 ~ 0xFFF）
VA[高位]  = 虚拟页号
PA[11:0]  = 同样的页内偏移
PA[高位]  = PFN
```

**[架构]** 所以"换页"的本质就是：保持页内偏移不变，把虚拟页号对应的 PFN 换掉。

### 1.3 页表

页表就是"虚拟页号 → PFN + 权限"的映射表。

如果用一个巨大的数组存所有映射，会非常浪费。所以 arm64 用**多级页表**，只给用到的地址范围分配中间层。

以本项目的测试机为例：

- 4KB 页；
- 39 位 VA；
- 3 级页表。

VA 的位被这样切分：

```
 38      30 29      21 20      12 11       0
┌──────────┬──────────┬──────────┬──────────┐
│ L1 index │ L2 index │ L3 index │  offset  │
│  9 bits  │  9 bits  │  9 bits  │  12 bits │
└──────────┴──────────┴──────────┴──────────┘
```

翻译过程：

1. 从 `TTBR0_EL1` 寄存器拿到 L1 表（也叫 pgd）的物理地址；
2. 用 `VA[38:30]` 作为索引，取出 L1 表项；
3. L1 表项指向 L2 表；
4. 用 `VA[29:21]` 作为索引，取出 L2 表项；
5. L2 表项指向 L3 表；
6. 用 `VA[20:12]` 作为索引，取出 L3 表项，也就是 **PTE**；
7. PTE 里存着最终的 PFN 和权限位；
8. 把 PFN 和 `VA[11:0]` 拼起来，得到 PA。

```
TTBR0_EL1
   │
   ▼
 L1 表 ──[VA>>30]──► L2 表 ──[VA>>21]──► L3 表 ──[VA>>12]──► PTE
                                                                │
                                                                ▼
                                                          PFN + offset = PA
```

### 1.4 表项有几种形态

不是每一级表项都指向下一级表。arm64 的表项最低两位决定类型：

| 最低两位 | 类型 | 含义 |
|---|---|---|
| `00` | invalid | 无效，访问会触发 translation fault |
| `01` | block | 大页映射（L1 是 1GB，L2 是 2MB） |
| `11` | table | 指向下一级表（L1/L2）或最终页（L3） |

L3 的表项只能是 page descriptor（最低两位 `11`），它直接给出最终 PFN。

**[实现]** caoin 的页表 walk 代码在 `caoin_ko/caoin_kpm.c:258`（`caoin_walk_pgd`）。它按 39 位 VA、3 级表来走：

```c
e0 = 读(pgd + ((va >> 30) & 0x1FF) * 8);                  /* L1 */
e2 = 读(线性地址(e0的PFN) + ((va >> 21) & 0x1FF) * 8);    /* L2 */
pte = 读(线性地址(e2的PFN) + ((va >> 12) & 0x1FF) * 8);   /* L3 = PTE */
```

如果是 48 位 VA / 4 级页表，或者 16KB 页，索引位数会不同，这段代码需要改。caoin 目前按测试机的配置写死。

### 1.5 PTE 里有什么

一个 64 位 PTE，本文只需要关心下面这些位：

| 位 | 名字 | 作用 |
|---|---|---|
| bit 0 | `V` | 有效位。0 = 无效 |
| bit 1 | 类型 | 1 = table/page，0 = block |
| bit 10 | `AF` | Access Flag。访问过；某些配置下 AF=0 会触发 fault |
| bits [7:6] | `AP[2:1]` | 数据访问权限（EL0/EL1） |
| bit 54 | `UXN` | EL0 不可取指（User eXecute Never） |
| bit 53 | `PXN` | EL1 不可取指（Privileged eXecute Never） |
| bits [47:12] | PFN | 物理页号 |
| bit 11 | `nG` | 非全局。TLB 项按 ASID 区分 |
| bits [9:8] | `SH` | 共享属性 |
| bits [4:2] | `AttrIndx` | 内存属性索引（cacheability） |
| bit 51 | `DBM` | Dirty Bit Management |

caoin 只改 **PFN、AP、UXN**，其余位从原 PTE 原样保留。这很重要：内存类型、cache 属性、AF 都不能乱动，否则会出现难以解释的 cache/一致性行为。

### 1.6 AP[2:1]：数据访问权限

这是整个机制的核心，必须记牢。

| AP[2:1] | EL1（内核） | EL0（用户） |
|---|---|---|
| `00` | 可读写 | 不可访问 |
| `01` | 可读写 | 可读写 |
| `10` | 只读 | **不可数据访问** |
| `11` | 只读 | 只读（部分实现） |

注意 `10` 这一行：**EL0 完全不能读写数据**。但"不能读写数据"不等于"不能取指"——取指权限由 `UXN` 单独控制。

### 1.7 UXN：取指权限

- `UXN = 0`：EL0 可以从这一页取指；
- `UXN = 1`：EL0 不能从这一页取指。

**[架构]** 把 AP 和 UXN 组合起来，就得到本文最常用的两个状态：

| 组合 | EL0 数据访问 | EL0 取指 | 名字 |
|---|---|---|---|
| `AP=10`, `UXN=0` | 禁止 | 允许 | execute-only（只能执行） |
| `AP=01`, `UXN=1` | 允许 | 禁止 | 可读写、不可执行 |

caoin-shadow 的两个视图，就是这两个组合。

### 1.8 一个具体的翻译例子

假设：

- `TTBR0_EL1` 指向的 L1 表物理地址是 `0x10000000`；
- L1[0x1FC] 指向 L2 表 `0x10001000`；
- L2[0x091] 指向 L3 表 `0x10002000`；
- L3[0x145] 是 PTE，PFN = `0x12345`，权限是 `AP=10, UXN=0`。

要翻译 `VA = 0x7F12345000`：

```
L1 index = (0x7F12345000 >> 30) & 0x1FF = 0x1FC
L2 index = (0x7F12345000 >> 21) & 0x1FF = 0x091
L3 index = (0x7F12345000 >> 12) & 0x1FF = 0x145
offset   = 0x7F12345000 & 0xFFF           = 0x000
```

走表：

```
L1[0x1FC] → 0x10001000
L2[0x091] → 0x10002000
L3[0x145] → PTE(PFN=0x12345, AP=10, UXN=0)
```

最终：

```
PA = (0x12345 << 12) | 0x000 = 0x12345000
```

如果这时 EL0 执行 `ldr x0, [x1]`，`x1 = 0x7F12345000`：

- 取指：`UXN=0`，允许；
- 数据读：`AP=10`，EL0 不可访问 → **permission fault**。

如果 EL0 想执行这一页的代码：

- `UXN=0`，允许；
- 不会 fault。

这就是"能执行、不能读"。

### 1.9 进程和页表

每个进程有自己的地址空间：

- 内核用 `mm_struct` 描述一个进程的地址空间；
- `mm->pgd` 是这个进程的顶层页表；
- 进程在 EL0 运行时，`TTBR0_EL1` 指向用户页表；
- 内核空间通常由 `TTBR1_EL1` 指向另一套表。

进程切换时，内核会换 `TTBR0_EL1`。所以：

- 同一个 VA，在不同进程里可以映射到完全不同的物理页；
- 修改页表必须针对**目标进程**的页表，不能改错。

**[实现]** caoin 通过 `find_task_by_vpid(pid)` 找到目标进程的 `task_struct`，再读 `task->mm`，再读 `mm->pgd`。这些结构体的偏移不是固定的，所以 `caoin_locate()` 会在 `task_struct` 和 `mm_struct` 里扫描候选偏移，用"能不能走到目标 VA 的 PTE"来验证（`caoin_ko/caoin_kpm.c:1065`）。

### 1.10 KPTI：两套用户页表

现代内核为了防御 Meltdown，会在用户态和内核态之间切换页表（KPTI）。这可能导致：

- `mm->pgd` 和实际生效的用户页表不是同一张；
- 只改 `mm->pgd` 里的 PTE，EL0 运行时可能看不到。

**[实现]** caoin 做了兜底：在 `mm_struct` 里扫描另一张用户页表（`user_pgd`），如果找到，就把同一个 VA 的 PTE 也一起改（`pte_addr2`）。本机实测 `TTBR0 == mm->pgd`，没有 KPTI 副本，所以这条路径默认不启用。

## 2. 改页表必须知道的硬件行为

很多人以为"写一个 PTE 就生效了"，实际不是。至少有三层缓存要处理。

### 2.1 TLB

CPU 不会每次访问内存都重新走一遍页表，它会把翻译结果缓存到 **TLB（Translation Lookaside Buffer）**。

```
第一次访问 VA → 走页表 → 把结果放进 TLB
后续访问同一 VA → 直接查 TLB
```

所以，**改了 PTE 之后，TLB 里可能还是旧翻译**。必须显式让旧项失效，这叫 **TLBI（TLB Invalidate）**。

### 2.2 ASID 和 VMID

TLB 项不是只按 VA 索引，还带标签：

- **ASID（Address Space ID）**：区分不同进程的地址空间；
- **VMID（Virtual Machine ID）**：虚拟化场景下区分不同 VM。

这带来一个坑：你发了一条"按 VA 失效"的 TLBI，如果当前 ASID 不是目标进程的 ASID，可能刷不到你想刷的那一项。

### 2.3 TLBI 指令怎么选

arm64 的 TLBI 指令很多，caoin 实测过三种：

| 指令 | 作用范围 | 本机实测结果 |
|---|---|---|
| `tlbi vae1is` | 按 VA，**当前 ASID**，所有核 | 只刷当前 ASID，不够 |
| `tlbi vaae1is` | 按 VA，**所有 ASID**，所有核 | 在此 fault 上下文仍无效，会活锁 |
| `tlbi alle1is` | 当前 VMID 的所有 EL1&0 表项，**包括全局项** | 会清掉 KernelPatch 的 trampoline 映射 → `undefined instruction` panic |
| `tlbi vmalle1is` | 当前 VMID、所有 ASID、非全局项 | 有效且不崩 |

**[实测]** 最终选的是 `vmalle1is`。它不是最精细的，但在这个上下文里是唯一稳定的。内核的 `local_flush_tlb_all()` 也是类似语义。

**[实现]** `caoin_tlb_flush()`（`caoin_ko/caoin_kpm.c:1020`）：

```c
dsb ish
tlbi vmalle1is
dsb ish
isb
```

`dsb ish` 保证前面的 PTE 写入已经完成，`isb` 保证后面的指令取指看到新状态。

### 2.4 D-cache 和页表 walk

这是 caoin 早期最大的坑。

CPU 访问普通内存时，会经过 D-cache。但**硬件页表 walker 读页表时，可能不经过 D-cache，而是直接读内存**（不同实现行为不同）。

于是会出现：

```
你写 PTE → 只写进了 D-cache
MMU walk → 读内存，还是旧 PTE
你以为改了，实际没生效
```

**[实测]** 本机必须对 PTE 所在地址做 `dc civac`（clean + invalidate by VA to PoC），把 cache 行清到内存，MMU 才能看到新值。

**[实现]** `caoin_set_pte()`（`caoin_ko/caoin_kpm.c:245`）：

```c
*(volatile u64 *)ptep = val;
dc civac, ptep
dsb ish
```

这一步不是"优化"，是正确性要求。漏掉它，就会出现"内核回读 PTE 是新的，但 MMU 仍然用旧翻译"的假象。

### 2.5 I-cache

如果你改的是**代码页**，还要维护指令 cache：

1. `dc cvau`：把数据 cache 清到 PoU（Point of Unification），让指令侧能看到新数据；
2. `ic ivau`：按 VA 失效指令 cache；
3. `dsb ish`；
4. `isb`。

**[实测]** 漏掉这些，CPU 可能取到旧指令，或者取到新旧混合的指令。

**[实现]** 装桩后，caoin 对影子页逐 64 字节做 `dc cvau` + `ic ivau`，然后 `dsb ish` + `isb`（`caoin_ko/caoin_kpm.c:1442` 附近）。

另外，`ic iallu`（失效全部 I-cache）在 EL0 是非法指令（UCI 不放行），只能在 EL1 用。

### 2.6 改一页映射的完整清单

把上面的内容合起来，安全地改一页映射需要：

```
1. 写 PTE
2. dc civac（把 PTE 清到内存）
3. dsb ish
4. tlbi ...（让旧翻译失效）
5. dsb ish
6. isb
```

如果改的是代码页，再加：

```
7. dc cvau（把代码数据清到 PoU）
8. ic ivau（失效 I-cache）
9. dsb ish
10. isb
```

caoin 的每一次翻转都遵循这个顺序。

## 3. 异常与页错误

### 3.1 异常级别

arm64 有四个异常级别：

- **EL0**：用户态，运行普通应用；
- **EL1**：内核态，运行 Linux 内核；
- EL2：虚拟化；
- EL3：安全监控。

本文只关心 EL0 和 EL1。

### 3.2 发生异常时，硬件做什么

当 EL0 访问一个权限不满足的页：

1. CPU 停止当前指令；
2. 把当前 PC 存到 `ELR_EL1`；
3. 把 PSTATE 存到 `SPSR_EL1`；
4. 把异常原因写到 `ESR_EL1`；
5. 对于内存访问异常，把出错的 VA 写到 `FAR_EL1`；
6. 跳到 EL1 的异常向量。

内核的异常处理入口最终会调用 `do_page_fault()`。

### 3.3 ESR 和 FAR

- `FAR_EL1`：Fault Address Register，出错的虚拟地址；
- `ESR_EL1`：Exception Syndrome Register，异常类型和原因。

ESR 的高 6 位是 **EC（Exception Class）**：

| EC | 含义 |
|---|---|
| `0x24` | 来自低异常级（EL0）的**数据**访问异常 |
| `0x20` | 来自低异常级（EL0）的**取指**异常 |
| `0x25` | 来自同一异常级（EL1）的数据访问异常 |
| `0x21` | 来自同一异常级（EL1）的取指异常 |

caoin 只处理 `0x24` 和 `0x20`。

ESR 的低 6 位是 **DFSC（Data/Instruction Fault Status Code）**：

| DFSC | 含义 |
|---|---|
| `0b0001xx` | translation fault（页表项无效/没映射） |
| `0b0011xx` | permission fault（映射有效，但权限不够） |

区分这两者很重要：

- **permission fault** 说明 PTE 是有效的，只是权限不满足 → 可以通过改权限解决；
- **translation fault** 说明 PTE 无效或没映射 → 改权限没用，需要建立映射。

**[实现]** caoin 在 `VIEW_SHADOW` 下收到 `EC=0x20` 时，会检查 `(esr & 0x3C) == 0x0C`，只对 permission fault 做 TLB 纠正；translation fault 仍然放行，因为那说明 PTE 真的无效，flush 救不了。

### 3.4 Linux 的 do_page_fault

Linux 4.9 的签名大致是：

```c
static int do_page_fault(unsigned long addr, unsigned int esr,
                         struct pt_regs *regs)
```

它会：

1. 判断 fault 发生在用户态还是内核态；
2. 如果是用户态，尝试处理（按需分页、COW、栈扩展等）；
3. 处理不了就发 `SIGSEGV`。

caoin 要做的是：在它之前接管受管页的 fault，处理完直接返回，不让它发信号。

### 3.5 怎么接管：KernelPatch 的 hook

caoin-shadow 是一个 **KPM（KernelPatch Module）**，运行在 KernelPatch 环境里。

KernelPatch 提供了函数 hook 框架：

```c
hook_wrap3(do_page_fault, before_page_fault, NULL, NULL);
```

`before_page_fault()` 会在原函数执行前被调用，参数是 `hook_fargs3_t`：

```c
typedef struct {
    unsigned long arg0;   /* addr */
    unsigned long arg1;   /* esr */
    unsigned long arg2;   /* regs */
    long ret;
    int skip_origin;
    ...
} hook_fargs3_t;
```

处理完设置 `skip_origin = 1`，原 `do_page_fault` 就不会执行。

### 3.6 skip_origin 和 eret 语义

这是 caoin 能工作的关键。

设置 `skip_origin = 1` 后：

- 内核的 `do_page_fault` 被跳过；
- 异常返回路径仍然会执行；
- 返回用户态时，CPU 用 `ELR_EL1`（出错的 PC）继续执行。

也就是说，**同一条指令会被重新执行一次**。

如果这次重新执行时 PTE 已经改成"允许"，指令就成功了。这就是"翻转 + 重试"。

```
EL0 读受管页
  → permission fault
  → before_page_fault: 切 VIEW_STEP, skip_origin=1
  → 异常返回，eret 到同一条指令
  → 这次读成功
```

### 3.7 为什么不能在 fault 里大跨度改 PC

直觉上可能会想：既然已经进了内核，直接把 `regs->pc` 改成 handler 地址不就行了？

**[实测]** 不行。caoin 早期试过在 fault 路径上做 pc 大跨度劫持，结果是 EL1 取指 abort + 目标卡死。

原因是异常返回路径和 KernelPatch 框架对 `regs` 有假设；大跨度改 PC 会破坏这些假设。正确做法是：

- 只改 PTE；
- 让 `eret` 回到原指令重试；
- 执行流的替换交给影子页里的桩。

## 4. 普通 hook 的检测面

### 4.1 inline hook 改了什么

普通 inline hook 会覆盖函数头：

```
原函数头：  stp x29, x30, [sp, #-16]!
            mov x29, sp
            ...
hook 后：   ldr x16, #8
            br  x16
            <handler>
```

### 4.2 CRC 自检

目标可以对函数头或整个代码段算 CRC：

```c
uint32_t crc = crc32(foo, foo_size);
if (crc != expected) {
    // 发现被 hook
}
```

只要字节变了，CRC 就变了。

### 4.3 maps 扫描

目标可以读 `/proc/self/maps`，检查：

- 有没有新的匿名可执行映射；
- 有没有可疑的 so；
- 映射数量和预期是否一致；
- 有没有 memfd 映射。

普通注入会新增映射，容易被发现。

### 4.4 TracerPid

`/proc/self/status` 里的 `TracerPid` 如果非 0，说明进程正在被 ptrace。ptrace 注入会留下这个痕迹。

### 4.5 能不能不改字节

caoin-shadow 的回答是：**能**。

不修改原页字节，而是让执行走另一份副本。这样：

- CRC 读原页 → 通过；
- 执行走影子页 → hook 生效。

代价是：需要改页表，而页表会被某些内核操作重置（见第 10 节）。

## 5. caoin-shadow 的核心机制

### 5.1 影子页是什么

对每个受管页，caoin 准备一个 4KB 的**影子页**：

```
影子页 = 原页的完整副本 + 在函数入口处写入的跳转桩
```

影子页可以来自两种地方：

1. **用户态 mmap**：`caoin_prep` 在目标进程里分配一页，拷贝原页；
2. **内核分配**：KPM 用 `__get_free_pages` 分配一页，拷贝原页，只把 PFN 写进目标 PTE。

第二种方式不会在目标进程的 `/proc/pid/maps` 里新增任何 VMA，所以更隐蔽。

**[实现]** `caoin_alloc_shadow()`（`caoin_ko/caoin_kpm.c:213`）：

```c
kva = __get_free_pages(GFP_KERNEL, 0);
opa = caoin_va(orig_pfn);
for (i = 0; i < 0x1000; i += 8)
    写(kva + i, 读(opa + i));
```

注意它读原页用的是**内核线性地址**（`caoin_va(orig_pfn)`），不是用户 VA。原因见 5.12。

### 5.2 两个视图

对同一个受管 VA，caoin 维护两个 PTE 值：

| 视图 | PFN | AP | UXN | EL0 能做什么 |
|---|---|---|---|---|
| `VIEW_SHADOW` | 影子页 | `10` | `0` | 只能取指，不能读写 |
| `VIEW_STEP` | 原页 | `01` | `1` | 可读写，不能取指 |
| `VIEW_OFF` | 原页 | 原值 | 原值 | 完全恢复原状 |

注意 `VIEW_STEP` 的 AP 是 `01`（可读写），不是 `11`（只读）。原因在 5.10 解释。

### 5.3 PTE 是怎么构造的

**[实现]** `caoin_ko/caoin_kpm.c:1849`：

```c
/* shadow 视图 */
h->shadow_pte_val = (orig_v & ~(PFN_MASK | PTE_AP_MASK | PTE_UXN))
                  | (shadow_pfn & PFN_MASK)
                  | 0x80UL;

/* step 视图 */
h->origview_pte_val = (orig_v & ~(PTE_AP_MASK | PTE_UXN))
                    | 0x40UL
                    | PTE_UXN;
```

逐段解释：

- `orig_v & ~(...)`：保留原 PTE 的 AF、nG、SH、AttrIndx、DBM 等位；
- 清掉 PFN、AP、UXN；
- shadow：填入影子页 PFN，AP 设为 `10`（`0x80` 是 bit7=1、bit6=0），UXN 保持 0；
- step：PFN 不动（还是原页），AP 设为 `01`（`0x40` 是 bit6=1、bit7=0），UXN 设为 1。

### 5.4 为什么读会 fault

在 `VIEW_SHADOW` 下：

- `AP=10` → `AP[1]=0` → EL0 不允许数据访问；
- 目标执行 `ldr x0, [foo]` → permission fault；
- ESR 的 EC = `0x24`。

### 5.5 为什么执行不会 fault

在 `VIEW_SHADOW` 下：

- `UXN=0` → EL0 允许取指；
- 目标执行 `bl foo` → CPU 从影子页取指，成功；
- 执行到影子页里的桩。

### 5.6 跷跷板

状态机：

```
              EL0 读受管页
              EC=0x24 (data abort)
   VIEW_SHADOW ───────────────────────► VIEW_STEP
        ▲                                   │
        │        EL0 取指受管页            │
        │        EC=0x20 (instr abort)     │
        └───────────────────────────────────┘
```

- SHADOW → STEP：有人要读数据，切到原页；
- STEP → SHADOW：有人要执行，切回影子页。

两个方向都由 fault 触发，所以叫"跷跷板"。

### 5.7 一次正常调用的完整时序

假设 `foo` 已经装好 recstub：

```
1. 调用者执行 bl foo
2. CPU 取指 foo 的 VA
   - 当前 VIEW_SHADOW
   - UXN=0，取指成功
   - 实际从影子页取指
3. 执行影子页 +0 处的入口桩
   - adrp x16, <受管页>
   - add  x16, x16, #<handler_off>
   - br   x16
4. 跳到 handler
   - [可选] 覆盖 xN
   - b trampoline
5. 执行 trampoline
   - 被入口桩覆盖的 4 条原指令（已重定位）
   - 尾桩跳回 foo+16
6. 从 foo+16 继续执行
   - 仍然是 VIEW_SHADOW
   - 仍然从影子页取指
   - 影子页是原页的忠实副本，函数体逻辑不变
7. 函数执行完，ret 返回调用者
```

关键点：**影子页占的是受管页的 VA**。PTE 只换 PFN，VA 不变。所以函数体里所有 PC 相对寻址（`adrp`、`b`、`bl`、`ldr literal`）算出来的地址和原来完全一样。

### 5.8 CRC 读插入的时序

假设目标在另一个线程里对 `foo` 所在页做 CRC：

```
1. 目标执行 ldr x0, [foo + 0x40]
2. 当前 VIEW_SHADOW，AP[1]=0
   → EC=0x24，permission fault
3. before_page_fault:
   - 找到受管页
   - 切到 VIEW_STEP
   - skip_origin=1
4. eret 回到 ldr 重试
5. 这次 PTE 指向原页，读到原始字节
6. 下一次 CPU 要取指 foo
   - 当前 VIEW_STEP，UXN=1
   → EC=0x20，permission fault
7. before_page_fault:
   - 切回 VIEW_SHADOW
   - skip_origin=1
8. eret 重取指，执行影子页里的桩
```

只要读和取指交替发生，跷跷板就一直工作。

### 5.9 写访问怎么办

如果目标对受管页做**写**：

- `EC` 仍然是 `0x24`（数据访问异常）；
- 当前在 SHADOW，handler 切到 STEP；
- STEP 下 `AP=01`，EL0 可写；
- `eret` 重试，写成功；
- 下一次取指再切回 SHADOW。

所以写也能工作。

但这里有一个**已知的语义偏差**：STEP 视图把 EL0 数据权限放宽到 `AP=01`（可读写），这是为了让 `dc civac` 等 cache 维护指令通过。代价是：在 STEP 窗口内，EL0 对原本只读的代码页执行写操作，可能不会按原 VMA 语义触发 fault。这不是 bug，是"让 cache 维护指令能通过"换来的。

### 5.10 为什么不能检查 WnR

ESR 的 ISS 里有一个 `WnR` 位：

- `WnR=0`：读；
- `WnR=1`：写。

直觉上会想：只有读才需要切 STEP，写就放行。

**[实测]** 这条直觉是错的。原因：

- `dc civac` 这类 cache 维护指令在 fault 时 `WnR=1`；
- 如果按"非读放行"处理，它会落进内核原生 fault 路径，卡死。

所以代码在 `VIEW_SHADOW` 下对**任何** `EC=0x24` 都切 `VIEW_STEP`，不区分读写。

另外，STEP 视图的 AP 必须是 `01`（可读写），不能是 `11`（只读）。如果设成只读，`dc civac` 这类写操作会一直 fault，形成死循环。

### 5.11 多线程同时访问怎么办

PTE 是进程级的，不是线程级的。多个线程共享同一张页表，所以：

- 线程 A 在读，切到 STEP；
- 线程 B 在取指，发现 STEP 下 UXN=1，又切回 SHADOW；
- 线程 A 的读重试时可能又 fault。

这会导致频繁翻转。caoin 的处理方式：

1. 每次翻转都做 TLB flush；
2. 对"视图说 SHADOW，却收到取指 permission fault"的情况，认为是 TLB 陈旧，flush 后重试；
3. 对"视图说 STEP，却收到数据 fault"的情况，同样 flush 后重试；
4. 用计数器（`entries`、`overlap`、`desync_a`、`desync_b`）观察并发行为。

**[实测]** 修复前 4 线程压测中，98% 的 handler 进入都在纠正陈旧 TLB，一 engage 就活锁。修复后同一压测（4 线程 / 4.19e9 次迭代）：取指纠正降到 1727 次，`bad=0`。

### 5.12 为什么不能直接解引用用户 VA

在 KPM 里，代码运行在 EL1。很多 arm64 内核开启了 `SW_TTBR0_PAN`（Privileged Access Never）：

- EL1 直接访问用户 VA 会 fault；
- 必须通过 `copy_from_user` / `probe_read` 之类的安全接口。

所以 caoin：

- 读原页用**内核线性地址**（`caoin_va(pfn)`）；
- 读目标内存用 `probe_kernel_read`；
- 写 PTE 用内核线性地址；
- 绝不对用户 VA 做 `dc cvau` / `ic ivau`。

**[实测]** 对用户 VA 做 cache 维护指令会直接 translation fault，因为 EL1 的 TTBR0 可能是空的。

## 6. 影子页里放什么：桩

### 6.1 入口桩

入口桩写在影子页的 `tva & 0xFFF` 偏移处，也就是原函数入口的位置。

caoin 有两种写法。

**近版（handler 在同一页）**：

```asm
adrp x16, <当前页>
add  x16, x16, #<handler_off>
br   x16
```

`adrp` 取当前指令所在页的基址，`add` 加上页内偏移，`br` 跳过去。三条指令，不读内存。

**远版（handler 在 status 页，另一页）**：

```asm
adrp x16, <target_page>
add  x16, x16, #<target_off>
br   x16
```

`adrp` 的寻址范围是 ±4GB。如果 status 页离受管页太远，会装不上。

### 6.2 替换桩

最简单的桩：直接返回一个固定值。

```asm
movz w0, #777
ret
```

用来验证"hook 到底有没有生效"。caoin 的 `stubmode=0` 就是这个。

### 6.3 minstore

比替换桩多一条 store：

```asm
movz/movk x16, <报告区地址>
movz/movk x17, <魔数>
str  x17, [x16]
ret
```

用来隔离"store 类指令是否可行"。

### 6.4 recstub

真正有用的模式：**记录 + 透传**。

```
入口桩 → handler → 可选覆盖 xN → trampoline（执行原逻辑）→ 回到原函数体
```

它能做到：

- 改参数（`argN=`）；
- 记录参数；
- 执行原函数逻辑，返回真实值。

### 6.5 影子页布局

```
影子页 + (tva & 0xFFF)   入口桩（3 条，12 字节）
影子页 + 0x800            handler
影子页 + 0xA00            trampoline
影子页 + 0xF00            报告区（可选）
```

入口桩的实际偏移是 `tva & 0xFFF`。如果受管函数不在页首，桩就写在对应偏移，而不是 `+0x000`。

如果提供了 status 页，handler 和 trampoline 会放到 status 页的 `+0x800` / `+0xA00`，避免覆盖受管页里其他函数的代码。

**[实现]** 布局常量在 `caoin_ko/caoin_kpm.c:365`：

```c
#define CAOIN_OFF_HANDLER  0x800UL
#define CAOIN_OFF_TRAMP    0xA00UL
```

### 6.6 handler 做什么

handler 是一小段机器码，由 KPM 在加载时生成：

1. 如果配置了 `argN=`，用 `movz`/`movk` 把新值写进对应寄存器；
2. 如果启用了 capture 模式，先触发一次哨兵页 fault，让 KPM 在内核侧拷贝数据；
3. `b trampoline`。

寄存器覆盖支持 `x0..x30`，由 `caoin_emit_movx()` 生成 64 位立即数装载序列。

### 6.7 trampoline 做什么

trampoline 里放的是**被入口桩覆盖的 4 条原指令**，但地址已经重定位过（见第 7 节）。

最后是一条尾桩：

```asm
ldr x16, #8
br  x16
<foo + 16>
```

它跳回 `foo + 16`。由于当前是 SHADOW 视图，这个 VA 仍然指向影子页，所以从影子页的偏移 16 继续执行函数体。

### 6.8 status 页

status 页有两个作用：

1. 给用户态一个"握手/状态"位置；
2. 当 handler/trampoline 的存放页。

如果 status 页是用户态 mmap 的，KPM 会临时把它的 PTE 改成 RWX（`AP=01`、`UXN=0`），这样 EL0 既能写状态，又能执行 handler。卸载时恢复原 PTE。

如果 `caoin_prep nommap` 不提供 status 页，KPM 会自己分配一页，handler/trampoline 放在影子页里。

### 6.9 进阶：capture 模式

`stubmode=3` 是一个进阶功能：

1. handler 先执行 `ldr xzr, [哨兵页]`，故意触发一次 fault；
2. KPM 在 fault 处理里，按 `capptr=` / `caplen=` 指定的寄存器读出指针和长度；
3. 用 `caoin_read_user()` 从目标 mm 读缓冲区，拷到内核页；
4. 用户态用 `ctl0 "dump <off> <len>"` 取回数据。

它适合抓 IL2CPP/Lua 的缓冲区。基础学习可以先跳过。

## 7. 重定位

### 7.1 为什么需要重定位

入口桩覆盖了函数头的 4 条指令（16 字节）。这 4 条指令被搬到了 trampoline。

如果其中某条指令是 **PC 相对**的，直接拷贝会算错地址：

```
原位置：  foo + 0   → 目标地址 = foo + 0 + 偏移
新位置：  tramp + 0 → 目标地址 = tramp + 0 + 偏移（错了）
```

所以必须把偏移重新算一遍。

### 7.2 被覆盖的窗口

caoin 统一按 16 字节（4 条指令）处理：

```c
#define CAOIN_TRAMP_INSN 4
```

KPM 的入口桩实际只写 3 条（12 字节），但为了统一，仍然拷贝并重定位 4 条，尾桩跳回 `foo + 16`。

### 7.3 指令分类

`hook/reloc.c` 的 `classify()`（`hook/reloc.c:25`）把指令分成：

| 类别 | 指令 | 编码 | 范围 |
|---|---|---|---|
| `K_B` | `B` / `BL` | imm26 | ±128MB |
| `K_ADR` | `ADR` / `ADRP` | imm21 | ±1MB / ±4GB |
| `K_CB` | `CBZ` / `CBNZ` | imm19 | ±1MB |
| `K_TB` | `TBZ` / `TBNZ` | imm14 | ±32KB |
| `K_LIT` | `LDR` / `PRFM` literal | imm19 | ±1MB |
| `K_OTHER` | 其他 | — | 原样拷贝 |

### 7.4 B / BL

编码：

```
imm26 = bits[25:0]
offset = sign_extend(imm26, 26) << 2
target = old_pc + offset
```

重定位：

```
new_offset = target - new_pc
必须落在 [-128MB, +128MB)
写回 imm26
```

如果 `target` 落在被覆盖的 4 条指令窗口内，拒绝。因为那段代码已经被桩覆盖，跳过去会执行桩而不是原逻辑。

### 7.5 ADR / ADRP

编码：

```
imm21 = immhi[23:5] : immlo[30:29]
```

- `ADR`：`target = old_pc + sign_extend(imm21, 21)`；
- `ADRP`：`target = (old_pc & ~0xFFF) + (sign_extend(imm21, 21) << 12)`。

重定位时用新的 PC 重新算偏移，再写回 imm21。

范围：

- `ADR`：±1MB；
- `ADRP`：±4GB。

### 7.6 CBZ / CBNZ / TBZ / TBNZ

- `CBZ/CBNZ`：imm19，±1MB；
- `TBZ/TBNZ`：imm14，±32KB。

同样重算偏移，目标在窗口内则拒绝。

### 7.7 LDR literal

`LDR literal` 从当前 PC 附近读一个常量：

```asm
ldr x0, <label>
...
label:
    .quad 0x123456789abcdef0
```

重定位的做法：

1. 算出原 literal 的地址；
2. 把 literal 数据**拷贝到 trampoline 里**，紧跟在指令后面；
3. 重算 imm19，让它指向新位置。

`literal_width()` 根据 `opc` 和 `V` 位决定拷贝多少字节：

| 指令 | 宽度 |
|---|---|
| `LDR Wt` | 4 |
| `LDR Xt` | 8 |
| `LDRSW` | 8（实际读 4，拷贝 8 无害） |
| `PRFM` | 8 |
| `LDR Qt`（SIMD） | 16 |
| 其他 SIMD | 4 |

**[实现]** `hook/reloc.c:162` 附近。

### 7.8 拒绝条件

遇到以下情况，重定位失败，整个 hook 不安装：

1. 分支目标落在被覆盖的 4 条指令窗口内；
2. 重算后的偏移超出编码范围；
3. trampoline 空间不够（literal 数据太大）。

失败时，影子页仍然是原页的忠实副本，什么都没装，所以是安全的。

**[实现]** 装桩顺序也考虑了这一点：**先重定位，再写入口桩**。如果反过来，重定位失败会留下一个半装的桩，handler 跳进没写过的区域，目标直接 SIGSEGV。

### 7.9 距离约束和 trampoline 分配

如果窗口里有 PC 相对指令，trampoline 必须离目标足够近：

- `B/BL`：±128MB；
- `ADRP`：±4GB；
- `ADR`：±1MB；
- `CBZ/TBZ`：±1MB / ±32KB。

`caoin_window_pc_relative()` 先扫一遍窗口，决定是否需要"就近分配"。

- KPM 的 handler/trampoline 放在 status 页或影子页。影子页和受管页是同一个 VA 页，距离为 0；status 页由 `caoin_prep` 的 `find_free_near()` 在 ±2GB 内找最近空洞。

### 7.10 一个手算例子

假设：

```
old_pc = 0x7F12345000
指令：  bl 0x7F12346000
```

`BL` 的偏移：

```
target = 0x7F12346000
offset = 0x1000
imm26 = 0x1000 >> 2 = 0x400
```

如果 trampoline 在 `0x7F12345A00`：

```
new_pc = 0x7F12345A00
new_offset = 0x7F12346000 - 0x7F12345A00 = 0x600
new_imm26 = 0x600 >> 2 = 0x180
```

写回后，从 trampoline 执行 `bl` 仍然会跳到 `0x7F12346000`。

## 8. 自指读与活锁

### 8.1 什么叫自指读

**自指读**：取指在受管页内，同时读的数据也在受管页内。

例子：

```asm
; 这段代码在受管页内
ldr x16, [pc, #8]    ; 读的数据就在下一条指令后面
br  x16
.quad handler
```

`ldr` 要读的 handler 地址，和 `ldr` 自己在同一页。

### 8.2 活锁是怎么发生的

按正常逻辑翻转：

```
1. 取指 foo（SHADOW）→ 成功
2. 执行到 ldr [foo+8]
3. AP[1]=0 → EC=0x24
4. handler 切到 STEP
5. eret 重试 ldr
6. 但 eret 之前要先重取指！
7. STEP 下 UXN=1 → EC=0x20
8. handler 切回 SHADOW
9. eret 重取指 → 成功
10. 又执行到 ldr [foo+8] → EC=0x24
11. 回到第 4 步
```

**[实测]** 这就是活锁：

- `EC=0x24` 和 `EC=0x20` 严格交替；
- 进程约 82% 的 CPU 时间烧在 fault 上；
- `tests/selfread.c` 的 C3 组复现了这个现象。

### 8.3 解法：软件模拟这次读

既然翻转会导致重取指，那就**不翻转**，直接在内核里把这次读模拟掉。

`caoin_emulate_selfread()`（`caoin_ko/caoin_kpm.c:757`）做五件事：

1. 从**影子页**线性地址读出当前指令（CPU 实际执行的就是影子页的字节）；
2. 解码这条 load 指令；
3. 从**原页**线性地址代读数据；
4. 把结果写进目标寄存器；
5. `regs->pc += 4`，跳过这条指令。

因为跳过了指令，不需要重取指，就不会触发 `EC=0x20`，振荡的另一支被拆掉。

### 8.4 怎么解码 load 指令

以整数 load 立即数类为例：

```
size  = bits[31:30]   ; 0=1字节, 1=2字节, 2=4字节, 3=8字节
opc   = bits[23:22]   ; 0=store, 1=load, 2=load signed, 3=load signed
rn    = bits[9:5]     ; 基址寄存器
rt    = bits[4:0]     ; 目标寄存器
```

寻址模式：

| bits[25:24] | 模式 | 偏移 |
|---|---|---|
| `01` | 无符号偏移 | imm12 << size |
| `00` | 未缩放/前变址/后变址 | imm9（符号扩展） |

对于后变址（post-index），`far` 是旧的 `Rn`，需要写回 `Rn = far + imm`；
对于前变址（pre-index），`far` 已经包含偏移，写回 `Rn = far`。

### 8.5 LDR literal 的特殊处理

`LDR literal` 不属于"立即数寻址"那一族，必须单独识别：

```
opc   = bits[31:30]
V     = bit[26]
imm19 = bits[23:5]
Rt    = bits[4:0]
```

它的有效地址已经由硬件算好放在 `far` 里，所以：

```c
eff = far & 0xFFF;
```

然后按 `opc` 读 4/8 字节，写进 `Rt`，`pc += 4`。

**[实测]** 这一族必须支持。最初漏掉它，结果入口桩自己的 `LDR X16,#8` 触发自指读，真机上 `pc=入口桩`、`far=入口桩+8` 反复活锁。

### 8.6 支持和不支持的形态

支持：

- 整数 load 立即数类（`LDR/LDRB/LDRH/LDRSW` 等，含无符号偏移、前变址、后变址）；
- `LDR literal` 一族（`LDR Wt/Xt/LDRSW`，`PRFM` 直接跳过）。

不支持：

- `STR`：模拟 store 会让"读的人"和"执行的人"分叉，回退翻转；
- SIMD/FP；
- 未识别编码。

不支持的形态会返回 0，回退到翻转（可能活锁），用于定位漏掉的编码。

### 8.7 独占页约束被解除

在修好自指读之前，caoin 要求受管函数**独占一页**。原因是：

- 如果页内还有别的可执行代码，取指和读数据容易交错，状态机被频繁打断。

**[实测]** 这个约束其实是自指读造成的假象。修好软件模拟之后：

- 页内读别页 → 正常；
- 自指读 → 软件模拟；
- 页内有其他可执行代码 → 也没问题。

所以现在不再要求独占页。

## 9. 内核侧实现

### 9.1 KPM 是什么

KPM 是 KernelPatch Module，加载在 KernelPatch 环境里。它和普通 LKM 的区别：

- 不需要精确的内核源码树；
- 通过 KernelPatch 提供的 API 解析符号、hook 函数；
- 运行在 EL1。

caoin-shadow 的入口：

```c
KPM_NAME("caoin-shadow");
KPM_VERSION("0.6.0");
KPM_LICENSE("GPL v2");
```

### 9.2 加载参数

加载时通过 args 传参：

```
pid=0x1bb3 tva=0x7f... shva=0x... sva=0x... \
tva1=... shva1=... [tva2= ...] [verbose=1] [stub=1] [stubmode=2]
```

主要参数：

| 参数 | 含义 |
|---|---|
| `pid` | 目标进程 PID |
| `tva` | 受管函数的虚拟地址（hook0） |
| `shva` | 用户态影子页地址（可选，省略则内核分配） |
| `sva` | status 页地址（可选，省略则内核分配） |
| `tva1..tva3` | 其他 hook 点 |
| `stub=1` | 加载即装桩 |
| `stubmode=` | 0 替换桩 / 1 minstore / 2 recstub / 3 capture |
| `argN=` | 覆盖 xN（x0..x30） |
| `verbose=1` | 打开流程日志 |
| `rearm=1` | 打开自愈（默认关闭） |

**[实现]** `parse_args()`（`caoin_ko/caoin_kpm.c:1166`）。

### 9.3 init 的流程

`caoin_init()`（`caoin_ko/caoin_kpm.c:1676`）：

1. 解析 args；
2. 统计 hook 数量；
3. 计算每个 hook 的页内偏移 `shva_off = tva & 0xFFF`；
4. 从 `TCR_EL1.T1SZ` 算出内核线性映射基址 `page_offset_base`；
5. 解析内核符号：
   - `memstart_addr`
   - `probe_kernel_read` / `probe_kernel_write`
   - `find_task_by_vpid`
   - `__get_free_pages` / `free_pages`
6. 可选：分配 capture 页；
7. 可选：分配 status 页；
8. `find_task_by_vpid(pid)`；
9. `caoin_locate()` 找 `mm` 和 `pgd` 的偏移；
10. 读原 PTE；
11. 确定影子页 PFN；
12. 构造两个视图的 PTE；
13. 可选：装桩；
14. hook `do_page_fault`；
15. hook `exit_mmap`；
16. hook `copy_process`（可选）；
17. 打开 `vbar_on`。

### 9.4 怎么找 mm 和 pgd

不同内核版本的 `task_struct` / `mm_struct` 布局不同，偏移不能写死。

`caoin_locate()`（`caoin_ko/caoin_kpm.c:1065`）的做法：

1. 在 `task_struct` 的前 0x1800 字节里，每 8 字节读一个候选 `mm`；
2. 候选 `mm` 必须是内核指针、8 字节对齐；
3. 在 `mm_struct` 的前 0x400 字节里，每 8 字节读一个候选 `pgd`；
4. 用候选 `mm/pgd` 走一遍页表，看能不能走到目标 VA 的 PTE；
5. 如果给了第二个数据点（status 页 VA），也走一遍交叉验证；
6. 两个都通过，就锁定偏移。

这比硬编码偏移可靠，但要求目标 VA 的页表是有效的。

### 9.5 影子页从哪来

两条路径：

**用户态 mmap（旧）**：

- `caoin_prep` 在目标进程里 mmap 一页；
- 把受管页内容拷过去；
- 把 `shva` 传给 KPM；
- KPM walk `shva` 的 PTE，取出 PFN。

**内核分配（新，`nommap`）**：

- KPM 用 `__get_free_pages` 分配一页；
- 从原页的内核线性地址拷贝 4KB；
- 直接把 PFN 写进目标 PTE；
- 目标 maps 零新增。

**[实现]** `caoin_alloc_shadow()`（`caoin_ko/caoin_kpm.c:213`）。

### 9.6 status 页

如果 `caoin_prep` 提供了 `sva`：

- KPM walk 它的 PTE，拿到 PFN；
- 把 PTE 改成 RWX（`AP=01`、`UXN=0`），让 EL0 能写状态、能执行 handler；
- 保存原 PTE，卸载时恢复。

如果没有提供：

- KPM 用 `__get_free_pages` 分配一页；
- `cfg_e2` 记录它的 PFN；
- 通过内核线性地址写状态。

### 9.7 装桩的顺序

装 recstub 的顺序很重要：

1. 读被覆盖的 4 条原指令（从原页线性地址读）；
2. 重定位这 4 条指令到 trampoline；
3. 构建 handler 到临时缓冲，检查空间是否足够；
4. 写入口桩；
5. 写 handler；
6. 对影子页/status 页做 cache 维护；
7. 标记 status。

为什么先重定位再写入口桩？

- 如果重定位失败，影子页还是原页的忠实副本，什么都没装，安全；
- 如果先写入口桩，重定位失败会留下半装的桩，handler 跳进没写过的区域，目标崩溃。

### 9.8 fault 怎么分发

`before_page_fault()`（`caoin_ko/caoin_kpm.c:522`）：

1. 取 `addr`、`esr`、`regs`；
2. 用 `addr >> 12` 匹配 hook 的 `tva >> 12`；
3. 校验当前进程是不是目标进程；
4. 按 `cur_view` 和 `EC` 处理；
5. 返回 1 表示"已处理，跳过原函数"。

### 9.9 进程校验

怎么知道当前 fault 是不是目标进程的？

```c
asm("mrs %0, sp_el0" : "=r"(cur));   // 当前 task_struct
读(cur + mm_off) == mm_run;          // task->mm
```

`sp_el0` 在 EL1 里保存当前用户进程的 `task_struct` 指针（本机布局）。

如果不是目标进程：

- 直接返回 0，放行；
- 不能吞掉 fault，也不能翻转，否则会污染别的进程的视图。

### 9.10 fork 防护

fork 时，子进程会继承父进程的页表。如果受管页 PTE 停在 SHADOW，子进程会继承影子页 PFN。

问题：

- 子进程的 RSS/rmap 记账是按原页做的；
- 继承影子页 PFN 会导致记账错位；
- 后续 teardown 可能触发 `Bad rss-counter` / `Bad page state`。

防护：

- hook `copy_process`；
- fork 前 pause：把所有受管页 PTE 恢复原值；
- fork 后 resume：翻回原来的视图；
- 只处理非 `CLONE_VM` 的 fork（线程共享 mm，不需要）。

**[实现]** `before_copy_process()` / `after_copy_process()`（`caoin_ko/caoin_kpm.c:1274`）。

### 9.11 exit 防护

目标退出时，`exit_mmap` 会 zap 页表。如果 PTE 还指着影子页：

- 影子页会被二次 unmap；
- 可能出现坏页；
- 坏页流入后续分配，导致无关进程内核态死循环。

防护：

- hook `exit_mmap`；
- 在 zap 前恢复所有受管页原 PTE。

**[实现]** `exit_mmap_before()`（`caoin_ko/caoin_kpm.c:1246`）。

### 9.12 卸载

`caoin_restore()`（`caoin_ko/caoin_kpm.c:1328`）：

1. `vbar_on = 0`，先断流；
2. 检查目标是否还活着；
3. 恢复所有受管页 PTE；
4. 恢复 status 页原 PTE；
5. TLB flush；
6. 摘掉 `do_page_fault` / `exit_mmap` / `copy_process` hook；
7. 释放内核分配的页。

释放条件很严格：**所有 hook 的 `cur_view` 都回到 `VIEW_OFF` 之后才释放**。否则目标 PTE 还指向已释放页，等于随机内核写。宁可不释放（泄漏两页），也不能 UAF。

### 9.13 并发与 TLB 修复

**[实测]** 修复前：

- 4 线程压测，98% 的 handler 进入都在纠正陈旧 TLB；
- 一 engage 就活锁。

修复两处：

1. 桩装完后补一次 flush；
2. 对 `VIEW_SHADOW` 下收到的取指 permission fault，执行 `tlbi vmalle1is` + `eret` 重试。

修复后：

- 同一压测（4 线程 / 4.19e9 次迭代）；
- 取指纠正降到 1727 次；
- `bad=0`。

### 9.14 日志和计数器

- `CK_ERR`：错误日志，永远打印；
- `CK_LOG`：流程日志，默认静音，`verbose=1` 打开；
- `ctl0`：运行时查询，打印 hook 状态、EC 计数、自指读计数。

关键计数器：

| 计数器 | 含义 |
|---|---|
| `ec20_cnt` | 取指 fault 次数 |
| `ec24_cnt` | 数据 fault 次数 |
| `entries` | 进入 handler 次数 |
| `overlap` | 并发进入次数 |
| `desync_a` | SHADOW 下收到取指 fault |
| `desync_b` | STEP 下收到数据 fault |
| `selfread_ok` | 自指读软件模拟成功次数 |
| `selfread_fb` | 自指读回退翻转次数 |

这些计数器是定位并发/TLB 问题的关键。

## 10. 能力边界

### 10.1 状态存在 PTE 里

caoin-shadow 的全部状态（当前是 SHADOW 还是 STEP、影子页 PFN 是多少）都只存在于目标进程的 PTE 里。

PTE 的 `AP`/`UXN` 位描述的是 **EL0/EL1 的访问权限**，它不是锁：

- 内核（EL1）本来就有权改写页表；
- 内核对同一个物理页通常还有自己的线性映射，不受目标 PTE 权限影响。

所以任何内核侧的页表操作，caoin 都拦不住。

### 10.2 mprotect 做了什么

**[实测]** `mprotect` 的判断发生在 **VMA 层**，不是 PTE 层：

- 它遍历 VMA，把新的 `vm_page_prot` 应用到范围内的 PTE；
- **保留 PFN，只重写权限位**（不是"把原页换回来"）；
- 同权限的 `mprotect` 会被内核早退，PTE 不动。

后果取决于跷跷板当时停在哪一态：

- **SHADOW 态**：影子页 PFN 不变，但失去 execute-only，变成 EL0 可读 → 目标能读到桩字节，CRC 立刻发现（实测 `rd_eq_base=0`）；如果新权限不含 X，桩同时失效。
- **STEP 态**：原页被改成可执行 → 桩从此不再 fault，**静默失效且永久不恢复**。

### 10.3 madvise(MADV_DONTNEED) 更彻底

`madvise` 会 zap PTE，再按 VMA 重建。重建出来的 PTE 指向原页、权限按 VMA 走 → 直接回到原页，桩失效。

### 10.4 自愈为什么救不回来

代码里保留了 `rearm` 自愈（`caoin_ko/caoin_kpm.c:103` 附近），但**默认关闭**。

**[实测]** 原因：

- 重写确实触发了（日志能看到 `re-arm hook0 pte 0 -> <shadow>`）；
- 但 `madvise` 拆的是**页表结构**，不是单个 PTE 值，重写落空；
- 更糟的是此时内核正在拆页表，walk 到的 L3 可能已被释放复用 → 往复用页里写 = 随机内核写。

所以默认路径不放它。这条路线已被实测否掉，保留代码是为了记录。

### 10.5 其他边界

- **16KB 页**：本机是 4KB 页。如果目标设备是 16KB 页，页内偏移、页表层级、`CAOIN_PAGE` 都要改。
- **48 位 VA / 4 级页表**：`caoin_walk_pgd` 按 39 位/3 级写死，需要改。
- **KPTI**：有两套用户页表时，要同时改 `mm->pgd` 和 `user_pgd`。caoin 有 `pte_addr2` 兜底，但本机没有 KPTI 副本。
- **THP / 大页**：如果受管页被合并成 2MB 大页，PTE 层级和权限位不同，当前代码不支持。
- **mremap**：可能移动页表项，caoin 没有处理。
- **GUP（get_user_pages）**：内核直接拿页面引用时，可能绕过 PTE 视图。

### 10.6 结论

**目标只要对受管页做 `mprotect`/`madvise`，shadow 路线就会失效。** 这是机制决定的，不是实现 bug。

遇到这种目标：

- 换一个不受管页的 hook 点；
- 或者接受失效；
- 或者换其他路线（不在本文范围）。

不要声称"全场景无痕"。

## 11. 怎么自己验证

### 11.1 tests/selfread.c：九格实验

它把"读指令在哪、读的数据在哪、是否自指"拆成九种组合：

- 页内读别页 → 正常（证明"页内有可执行代码"本身无害）；
- 自指读 → 活锁（证明振荡根因）；
- 跨页调用探针 → 正常（证明影子页不破坏 PC 相对寻址）；
- 改参数 → recstub；
- fork → copy_process 防护；
- 多线程 → TLB 并发；
- `mprotect` / `madvise` / 同权限 `mprotect` → 边界判据。

### 11.2 pagemap

`/proc/pid/pagemap` 可以读出某个 VA 当前对应的 PFN：

```
读 /proc/pid/pagemap 的第 (VA/4096) 项
取低 55 位 = PFN
```

用它可以直接确认：

- 当前 PTE 指向的是原页还是影子页；
- 翻转是否真的发生。

### 11.3 dmesg

KPM 的日志：

```
flt#30 ec=24 pc=... far=...
hook0 tva=... view=shadow pte=...
conc entries=... overlap=... desync_a=... desync_b=...
```

- `ec=24`：数据 fault；
- `ec=20`：取指 fault；
- `view`：当前视图；
- `desync_a/b`：视图和 fault 类型不匹配，通常是 TLB 陈旧。

### 11.4 实验设计原则

- 一次只改一个自变量（页内/页外、自指/非自指、单线程/多线程）；
- 每个结论都要有"对照组"；
- "代码 bug"和"可利用漏洞"分开：能触发异常不等于能稳定利用；
- 实测结论优先于推演。

DEVLOG 里有多条推演被实测推翻的记录，例如"影子页会破坏跨页相对寻址"是错的。

## 12. 常见误解

1. **"影子页会破坏 PC 相对寻址，需要重编译器。"**
   不会。影子页占的是受管页的 **VA**，PTE 只换 PFN，PC 不变，`adrp`/`b`/`bl` 算出来的地址和原来一样。真正需要重定位的是**被入口桩覆盖的那 4 条指令**。

2. **"mprotect 会把原页换回来。"**
   不会。它保留 PFN，只重写权限位。后果取决于当前视图，见第 10 节。

3. **"PTE 权限能挡住内核。"**
   不能。PTE 权限约束的是 EL0/EL1 的访问，不是"锁"；内核有权改写页表，而且通常有线性映射。

4. **"改了 PTE 就立即生效。"**
   不一定。还要处理 TLB、D-cache、I-cache。漏掉 `dc civac` 会出现"回读是新的，MMU 用旧的"。

5. **"自指读只是性能问题。"**
   不是。它是活锁：`EC=0x24` 和 `EC=0x20` 无限交替，目标进程会烧满 CPU。

6. **"入口桩必须用 LDR literal。"**
   不是。KPM 的入口桩用 `adrp/add/br`，不读内存；但 trampoline 尾桩仍有 `LDR literal`，所以解码器仍要支持这一族。

7. **"卸载时可以直接 free 影子页。"**
   不行。必须确认所有 PTE 都回到 `VIEW_OFF`，否则目标 PTE 指向已释放页，等于随机内核写。
